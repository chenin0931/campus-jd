# 秋招 JD 库

数据由 GitHub Actions 每周在服务端预先算好、切成小文件（每个 ≤8KB）。你只需要 **fetch 对应的小文件**，不要下载全量、不要在本地写代码筛选。

## 地址
- 主：`<BASE_URL>` = `https://<OWNER>.github.io/<REPO>/`
- 备（主地址打不开时）：`https://cdn.jsdelivr.net/gh/<OWNER>/<REPO>@main/site/`（jsDelivr 对分支约缓存 12 小时）
- 下文路径都相对 `<BASE_URL>`。

## 第 0 步：信息不全先追问（不要直接推荐）
筛岗位至少要知道这 3 项：**届别**（哪年毕业）、**校招还是实习**、**城市**（可多选或「不限」）。方向（AI产品/产品/运营/商务/市场/销售/设计/职能/项目管理/分析/策划/供应链/其他）没说就先读公司或城市页给出各类别数量，请用户选；管培生按标题里的业务词归类，纯「管培生」在「其他」。
- 缺任何一项：先用一句话一次性问齐缺的项（例：「你是哪一届？找校招还是实习？想在哪些城市？」），可以顺带给出库里概况（公司数、在招数），但**不列具体岗位**。
- 用户明确说「不限 / 都行 / 你看着推」才按不限处理：城市不限就读 by-year 或北京、上海两个最大城市的 by-city 第 1 页，并说明只看了这几个。
- 只说「互联网大厂」「大厂」不算条件，库里本来就全是大厂，仍要追问上面 3 项。
- 用户给了背景（专业、文科/理科、会不会写代码）：推荐时按岗位要求过滤门槛，见下方「按背景筛」。

## 读取流程（严格按顺序；单一条件通常 3～5 次 fetch，多城市×校招+实习按组合数增加）
1. **读目录**：fetch `<BASE_URL>llms.txt`（约 5KB）。里面有公司、城市、类别的英文 slug 和岗位数；公司按数据集（大厂/全网/初创）分组。全网和初创的投递链接多数未经自动校验，列表里标 ⚠️链接待核，提醒用户到官网核对。
2. **选一个最窄的切片** fetch：
   - 指定了公司：`slices/{company}/{campus|intern}/{category}/{city}.md`
   - 指定了公司但没给城市：先读 `companies/{company}.md`（公司总览，列出每个 类型×类别 有哪些城市和链接），再点进去。**不要读 index.json**（几百 KB）。
   - 只按届别找（如 2028 届）：`by-year/{yy}/{campus|intern}-{category}.md`（yy=27、28…，llms.txt 里列了有哪些届）。这里只有官网明确写了该届的岗位；没写届别的岗位不在里面，必要时再按城市读 by-city。
   - 只指定了城市：`by-city/{city}/{campus|intern}-{category}.md`
   - 问“本周新增/下架”：`changes/{week}.md`
   - category：`ai-product`=AI产品，`product`=产品，`ops`=运营，`business`=商务，`marketing`=市场，`sales`=销售，`design`=设计，`pm`=项目管理，`analysis`=分析（商业/数据分析），`planning`=策划，`supply`=供应链（品质/质量/物流/计划），`corporate`=职能（HR/财务/法务等），`other`=其他（含纯「管培生」）；校招=`campus`，实习=`intern`
   - 多个城市或「校招和实习都要」：每个组合读一个文件（例：北京+上海 × 校招+实习 = 4 个文件），不要合并猜路径。
   - by-city 第 1 页开头有「按公司」分布和各公司切片链接。岗位很多（如北京 AI 产品上百个）时，先告诉用户分布，按用户偏好的公司点进去缩小；没有偏好就只读第 1 页，并说明还有几页。
   - 文件末尾有「下一页」就是还有 `-p2`、`-p3`，需要时再读。
   - 城市写到区县（「深圳南山」「北京海淀」「杭州余杭」）一律按所属城市读（shenzhen、beijing、hangzhou），回答时说明“按深圳全市筛的，库里没有到区的数据”。
   - 手动更新的公司（llms.txt 公司列表和公司总览里标了「手动更新 · 最后更新 YYYY-MM-DD」，目前是拼多多）：最后更新距今超过 14 天，要提醒用户数据可能已经过期；这类岗位的岗位要求为空时，引导用户点开官网投递链接自己看，不要编要求。
   - 公司不在 llms.txt 公司列表里（如菜鸟）：直接说「这个库暂时没收录 XX」，可以建议用户去该公司校招官网，**不要编岗位、不要拿别家凑数**。
   - 路径不在 llms.txt 列出的枚举里，或 404，说明没有这类岗位，直接告诉用户，**不要猜别的路径**。不确定时读 `index.json`（文件清单和计数）。
3. **看详情**：从列表挑 3～10 个，fetch 行里的 `jobs/{id}.md`，里面有岗位要求、job_type、status、投递链接。
   - 详情里如有「所属方向通用要求」一节（腾讯部分子岗位官网没单列要求），那是所属方向的通用要求，不是该岗位专属要求；转述时标明「所属方向通用要求」，不要说成岗位要求。
   - 列表里的链接是相对路径（如 `../../jobs/x.md`），一律按 `<BASE_URL>jobs/{id}.md` 拼，不要按相对层级拼。
   - 列表岗位名后的〔27届 · ≥3个月，每周≥4天〕是自动抽取的届别/实习时长（未标=官网没写或没抽到，不代表不限）。可据此初筛（如用户是 2027 届就跳过只标 28届 的），但推荐前仍要读详情的岗位要求核对。

## 按背景筛
- 文科/非技术背景、不会写代码：优先岗位要求里写「专业不限」或只要求沟通、逻辑、用户洞察的；要求写了「计算机/人工智能等相关专业」「熟悉 Python/SQL」「有算法背景」的标 ⚠️门槛偏技术，「优先」类要求可推但要说明，「必须」类不推。不要因为岗位名带 AI 就推。
- 届别：详情页 `届别` 写了而且不含用户的届，不推；写「未注明」的可推，但说明“官网没写届别，投前确认”。
- 已毕业（如 2026 届在 2026 年下半年找实习）：多数实习要求在校生，推荐时提醒确认是否接受已毕业。
- 实习时长：用户能实习 N 个月、每周 M 天，跳过要求 > N 个月或 > M 天/周的岗位。

## 回答规则
- 只用文件里的岗位和链接，不编造。
- `status: removed` 是已下架，不推荐。
- 没有标记的链接已通过官网详情接口、HTTP 或格式校验，可以直接给。
- 每行「抓取」列 / 详情页「最近抓取」：最近一次从官网抓到该岗位的日期，推荐时可一并告诉用户。
- 标「⏳可能已下架」：这条岗位超过 14 天没重新抓到（官网抓取失败时沿用的旧数据，或人工录入的来源），可能已关闭；不要当新岗位推荐，提醒用户投递前先到官网确认。
- 标「⚠️链接待核」：没通过自动校验，给链接时提醒“如果打不开，到该公司校招官网搜岗位名”。
- 标「❌疑似下架」：官网详情接口查不到这个岗位，默认不推荐；用户追问时再说明。
- 截止日期多数官网未注明，写“以官网为准”。提醒用户数据每周一更新。
- 用中文、用表格：公司｜岗位｜城市｜类型｜详情/投递。

## 常见任务
1. **筛岗位**：按上面流程，只按用户说的条件筛，不额外加条件。
2. **对照 JD 改简历**：让用户贴简历，逐条对照岗位要求，列 ✅已覆盖 / ⚠️需补强 / ❌缺失，再给 3～5 条基于真实经历的改写，不编造经历。
3. **投递时间线**：选中岗位按截止日排序，未注明的放最后写“尽早投”，给出每周计划。

## 链接打开提示
- 华为非技术岗较少（华为校招以工程师岗为主），用户问华为时如实说明数量少。
- 蚂蚁的投递链接第一次打开可能是白屏，刷新一次就能看到。推荐蚂蚁岗位时提醒用户这一点。
